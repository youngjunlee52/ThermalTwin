## 처음 쓰는 분 (3분이면 됩니다)

함께 있는 영상 **`ThermalTwin_사용법.mp4`** 를 그대로 따라 하세요.

1. **준비:** Windows PC + Python 3.12 이상 (python.org, 설치 첫 화면에서 "Add python.exe to PATH" 체크)
2. **압축 풀기:** `C:\dev\ThermalTwin_v04` 처럼 짧은 영어 경로
3. **`1_setup.bat`** 더블클릭 (처음 한 번, 1–2분) → "SETUP COMPLETE" 확인
4. **`2_start.bat`** 더블클릭 → 브라우저가 자동으로 열림 (검은 서버 창은 닫지 않기)
5. 화면 맨 위 **"지금 배터리 상태"** 를 봅니다. 초록 **정상**이면 문제없음, 노랑 **주의**·빨강 **위험**이면 프로그램이 충전을 줄이고 냉각을 늘립니다
6. 모르는 단어 옆 ⓘ 에 마우스를 올리면 쉬운 설명, 오른쪽 위 **? 도움말** 로 안내 다시 보기
7. 잘 설치됐는지 확인: **`8_selftest.bat`** → 18개 항목이 모두 "통과"면 정상

화면은 두 갈래입니다. **운영** (배터리 상태 · 제어, 차량 · 연동) 은 누구나, **R&D** (센서 배치, PINN 모델, 냉각판 설계, 모델 설명) 는 분석용입니다.

## 리뷰 대응 2순위: SOH 추정이 노화와 외부 환경을 혼동하는 문제

- **원인 (버그):** 차량 모델은 `셀 저항 = R0(온도, SOC) + R_aging(SOH)` (BINN 노화식, 노화분은 온도와 무관)인데, 트윈은 노화분을 **25 °C 기준 저항**으로 역산했습니다. 뜨거울수록(R0 가 작을수록) 노화를 과대평가 → 덥고 냉각이 약할수록 SOH 가 낮게 나왔습니다.
- **수정 (`backend/estimator.py` 의 `SOHEstimator`):** 노화 저항 = 측정 저항 − **현재 추정 코어온도·SOC 의** R0. 전류가 충분하고 코어 10–45 °C, SOC 15–90 %, 코어 추정 일치(모델 차이 < 2 K)일 때만 천천히 갱신(유효 표본 약 500). 95 % 신뢰구간 = 표본 분산 + 코어온도 불확실성이 R0 를 통해 들어오는 계통 오차. 조건을 못 채우면 값을 내지 않고 '추정 중/보류'.
- **민감도 분석 (`backend/soh_sensitivity.py` → `models/soh_sensitivity.json`, 화면 R&D › PINN 모델):**

| 경우 | 이전 방식 | 새 방식 |
|---|---|---|
| 실제 85 %, 외기 10/25/40 °C × 유량 3/10/20 L/min (9가지) 최대 오차 | 4.8 %p | **0.2 %p** |
| 조건에 따른 흔들림 | 3.6 %p | **0.2 %p** |
| 실제 95 / 85 / 75 % (25 °C) | 93.4 / 82.8 / 71.1 | **94.7 / 84.9 / 75.0** (모두 95 % 구간 안) |
| 가혹 200 kW·40 °C·3 L/min, 실제 70 % | 66.0 (틀린 값) | **보류** (코어 추정 불확실) |
| 실차 재생: 충전 2구간 / 주행 1구간 | 76 / 76 / 85 | 추정 중(측정 부족) / **82.9 % (80.0–86.8)** |

- **한계:** 시뮬레이션 차량은 분극(RC) 전압이 없고 트윈과 같은 저항 구조를 써서 결과가 낙관적입니다. 실차는 R0·OCV 를 제조사 자료나 셀 시험으로 맞춰야 절대값을 믿을 수 있습니다 (지금 실차 값은 상대 비교용).

## 리뷰 대응 3순위: 국부 과열·센서 고장 검증 (`backend/robustness.py` → `models/robustness.json`, 화면 R&D › 센서 배치 분석)

조건: 급속충전 150 kW·25 °C·10 L/min, 균등 센서 16개, 25분. 시뮬레이션 차량에 셀별 냉각 불량 주입 기능(`cell_cool_scale`) 추가.

| 상황 | 코어 RMSE: 진단 없음 → 진단 사용 | 결과 |
|---|---|---|
| 정상 | 0.29 → 0.29 K | 오경보 0 (실차 3구간·가혹·주행·저온에서도 0) |
| 센서 −8 K 치우침 (차갑게) | 2.48 → **0.30 K** | 30 s 안에 격리 |
| 센서 서서히 어긋남 (−0.6 K/분) | 1.83 → **0.30 K** | 180 s 안에 격리 |
| 센서 값 고착 | 0.39 → 0.33 K | 300 s 안에 격리 |
| 센서 +8 K 치우침 (뜨겁게) | 2.15 → 1.88 K | 버리지 않고 그 셀에만 반영(안전 쪽 과대), 현장 확인 경고 |
| 센서 달린 셀 냉각 불량 | 2.46 → 1.63 K | 그 셀 0.1 K 이내로 포착 |
| 센서 절반 끊김 | 0.35 → 0.35 K | 원래 강건 |
| **센서 없는 셀 냉각 불량** | 0.68 → 0.68 K | **그 셀을 약 10 K 낮게 봄 — 센서 8·16·32·48개, 센서 바로 옆이어도 동일** |

- **센서 고장 진단 (`SensorFaultMonitor`)**: 각 센서를 나머지 센서로 예측(leave-one-out)해 혼자 튀는지 봄. 주변보다 *차갑게* 읽거나 값이 고착되면 열을 숨길 수 있어 격리. 주변보다 *뜨겁게* 읽으면 국부 과열일 수 있어 버리지 않고 그 셀에만 반영 + 현장 확인 경고. 히트맵에 ✕(격리)·!(혼자 뜨거움) 표시.
- **개발 중 발견한 위험**: 처음엔 뜨거운 센서도 격리했더니, 냉각 불량 셀의 *정상* 센서를 숨겨 과열을 9 K 놓쳤음 → 비대칭 규칙으로 수정. 실차 1 °C 분해능 프로브를 '고착'으로 오판한 오경보도 발견해 순 변화 기준으로 수정.
- **센서 없는 셀의 냉각 불량은 관측 불가**: 셀 사이 단열 패드(4 K/W) 때문에 한 셀의 과열이 이웃 센서에 거의 전달되지 않음. 셀 전압 저항 역산(셀 간 저항 편차 0.85–1.42배에 묻힘)과 모듈 냉각수 열수지(모델 차이 ±20–50 W > 신호 20 W)도 시도했지만 구분 불가. **센서 증설로는 해결되지 않으며**, 조립 공정 검사(갭필러 접촉), 셀별 온도 측정(셀마다 NTC·플렉서블 PCB), 임피던스 기반 셀 온도 측정 같은 하드웨어 대책이 필요.

## 리뷰 대응 4순위: 냉각판 최적 설계의 실제 적용 가능성 (화면 R&D › 냉각판 설계)

| 리뷰 지적 | 확인·구현 |
|---|---|
| 곡관·방향 전환 국부 손실 반영 여부 | 이미 반영돼 있었음 (180° 굽힘마다 K = 0.4 + 0.8·w/2r, 굽힘 수 = 통과 수 × 12). 냉각판 압력강하의 **7–56 %** 를 차지. 채널 입·출구 손실(K = 1.5)을 새로 추가하고 마찰·굽힘·입출구 내역을 표시 |
| 펌프 효율·운전 범위 | `backend/pump.py`: 12 V 전동 워터펌프 급 성능곡선(최대 양정 60 kPa·최대 유량 40 L/min, 상사법칙 회전수 조절) + 효율 지도(수력 최고 45 %·모터 60–85 %) + 냉각판 밖 루프 손실(18 kPa @ 20 L/min) + 냉각판 허용 압력 100 kPa. **모두 가정값 — 실제 펌프 사양서로 교체 필요** |
| 온도편차·실제 펌프 소비전력 함께 평가 | 운전 가능한 설계만 대상으로 **최고온도·온도편차·펌프 전기 소비 3목적 파레토** + 무릎점 추천 |
| CFD·고정밀 해석 비교 | 축약 모델 상위 후보 3개와 비교 항목·해석 설정·판정 기준(압력강하 ±20 %, 온도 ±1 K)을 담은 **CFD 검증 계획**을 결과에 포함. CFD 자체는 이 앱 범위 밖 |

결과 (150 kW·25 °C·냉각수 20 °C):
- 245개 설계 중 **140개는 펌프로 낼 수 없는 조합** (예: 폭 4·깊이 1 mm·25 L/min 은 냉각판 압력강하 2.6 MPa). 이전 방식(고정 효율 35 %·루프 손실 없음)은 펌프 전력을 최대 약 3배 과소평가.
- 추천: **폭 10·깊이 4 mm·15 L/min** — 최고 36.2 °C, 온도편차 4.2 K (목표 5 K 만족), 펌프 11.6 W (회전수 63 %). 이전 방식 추천(20 L/min)은 펌프 24.5 W 로 2배 이상인데 최고온도는 0.6 K 만 낮음.
- 마찰 +30 %, 굽힘 ×0.5/×2, 입출구 ×3 에서도 **추천이 바뀌지 않음** (압력손실 모델 불확실성에 강건).
- 200 kW·35 °C 에서는 운전 가능한 설계 중 온도편차 5 K 를 만족하는 것이 **없음** → 냉각판 형상만으로는 한계.
- 추천이 탐색 범위 끝(폭 10·깊이 4 mm)에 있어 더 넓은 범위 탐색 여지가 있음 (냉각판 두께·셀 폭 제약 확인 필요).
- 시뮬레이션 차량도 펌프 곡선과 만나는 유량까지만 흘립니다 (예: 폭 4·깊이 1 mm 에 25 L/min 요청 → 실제 0.9 L/min). 트윈은 차량이 보고한 실제 유량으로 계산하고, 화면은 요청 유량과 실제 유량을 함께 보여 줍니다.

참고: 고출력 충전에서는 PINN 신경망과 하이브리드의 차이가 3 K 를 넘어 안전 모드가 켜질 수 있습니다 (200 kW·25 °C 에서 충전 시간의 약 30 %, 가혹 조건 약 46 %). 학습 범위 끝에서 대표 모델이 약해지는 것을 안전 모드가 잡아내는 것이며, 그동안에도 온도는 보수적 규칙으로 지켜집니다. 150 kW·25 °C 정상 충전에서는 켜지지 않습니다.

| 센서 데이터로 열전달 식을 미리 학습해 사용 | `backend/models/pinn.npz` 에 학습 완료 가중치 포함, 서버가 바로 사용. 재학습 `5_retrain_models.bat` | — |

## 실행 (Windows)

1. Python 3.12 이상 설치 (설치 화면에서 "Add python.exe to PATH" 체크)
2. 압축을 `C:\dev\ThermalTwin_v04` 같은 짧은 영어 경로에 풀기 (이전 버전 폴더와 섞지 않기)
3. `1_setup.bat` (처음 한 번) → `2_start.bat` → 브라우저에서 http://localhost:8000 자동 실행
4. (선택) `4_demo_gateway.bat`: 외부 차량이 실시간으로 데이터를 보내는 시연 — 화면이 자동으로 '외부 수신'으로 바뀜
5. (선택) `5_retrain_models.bat`: PINN 재학습 + 센서 배치·실차 검증 다시 계산 (약 3분)
6. (선택) `6_demo_can_gateway.bat`: 가상 CAN 버스 시연 — 화면 위 '차량' 선택에서 `can_demo` 를 고르세요
7. (선택) `7_calibrate_pinn.bat`: `data\cell_test\*.csv` (코어 열전대 셀 시험)로 PINN 재보정

다른 기기(게이트웨이·라즈베리파이)에서 데이터를 받으려면 서버를 켜기 전에 토큰을 정하세요. 토큰이 없으면 이 PC 에서만 접속됩니다.
```powershell
$env:THERMALTWIN_INGEST_TOKEN = "아무도-모르는-긴-문자열"; .\2_start.bat
```

스마트 앱 컨트롤이 .bat 을 막으면 VS Code 터미널에서:
```powershell
python -m venv backend\.venv
backend\.venv\Scripts\python.exe -m pip install -r backend\requirements.txt
backend\.venv\Scripts\python.exe -m uvicorn main:app --app-dir backend --port 8000
```

## 외부 실시간 입력 형식 (BMS·CAN 게이트웨이 → ThermalTwin)

`ws://<PC IP>:8000/ws/ingest` 로 한 줄씩 JSON 을 보내면 매번 `{"type":"commands", "charge_limit_kw", "coolant_flow_lpm", "coolant_set_c", "reason"}` 가 돌아옵니다.
```json
{"t_s": 1200, "current_a": -320.5, "soc": 0.47, "v_cells": [3.912, ...96개],
 "probe_cells": [[0,1],[0,7]], "probe_t": [31.2, 32.0], "t_coolant_in": 20.5, "t_ambient": 25}
```
`"vehicle_id": "EV001"` 을 넣으면 차량마다 따로 처리합니다. 토큰을 정했다면 `?token=…` 또는 `Authorization: Bearer …` 를 붙입니다.
`tools/fake_bms_gateway.py` 가 JSON 예제, `tools/can_gateway.py` 가 CAN 버스 예제입니다.

```powershell
# 실제 CAN 장비 (PCAN 예시). 다른 차량은 --dbc 와 can_gateway.py 의 SIGNALS 표만 바꾸면 됨
backend\.venv\Scripts\python.exe tools\can_gateway.py --interface pcan --channel PCAN_USBBUS1 --bitrate 500000 `
  --dbc 차량.dbc --probe-map 프로브위치.json --vehicle EV001 --url wss://서버:8443/ws/ingest --token …
# CAN 로그 재생 (.asc .blf .log)
backend\.venv\Scripts\python.exe tools\can_gateway.py --log 주행.asc --vehicle EV001
```
TT_Command 는 권고 메시지입니다. BMS 가 자체 안전 판단 없이 그대로 적용하면 안 됩니다.

## 사용 범위 (앱의 R&D · 모델 설명 탭에도 있음)

- 제어 명령은 **권고**입니다. 실제 차량에서는 BMS 가 자체 안전 판단으로 받아들일지 정합니다.
- 실차 데이터의 코어 온도와 SOH 는 **같은 차량 안에서의 상대 비교용**입니다 (냉각 구조·OCV 표·프로브 위치가 공개되지 않아 가정값 사용).
- 열폭주 계산은 SEI 분해 단계(약 84 °C 부근 발열 시작)까지만 다룹니다.
